# Дизайн: сквозное шифрование (E2EE) в nullchat

Статус: согласован в обсуждении 06.11.2026, реализация по [плану](../plans/2026-11-06-e2ee.md). E2EE добавляется по прямому запросу, вне основной последовательности шагов `docs/PLAN.md`; это фиксируется отдельным решением 006 в `docs/ARCHITECTURE.md`.

## 1. Цель и модель угроз

Сервер (и всё, что видит его память, диск или трафик за TLS) не должен узнавать текст сообщений и название комнаты, не должен незаметно подменять ключи собеседников и не должен незаметно переставлять, повторять или подделывать сообщения.

| Противник | Что получает | Результат |
|---|---|---|
| Сервер / оператор, пассивно | Шифротексты, открытые ECDH-ключи, verifier | Не читает переписку и название; длина скрыта до блоков по 256 байт |
| Сервер, активно (подмена ключей) | — | Не может подписать чужой ключ без секрета ссылки; подмена ломает обмен и меняет код сверки |
| Сервер подменяет/повторяет/переставляет сообщения | — | Подмена ломает тег AES-GCM; повтор и перестановка видны по счётчику отправителя |
| Перехватчик ссылки без пароля | Ссылка | Может войти вместо гостя (гость увидит «приглашение использовано»); с паролем — не войдёт |
| Утечка ссылки и пароля после разговора | Ссылка, пароль | Переписку не раскрывает: ключ сообщений выведен из эфемерного ECDH, закрытые ключи жили только во вкладках |
| Сервер подменяет JavaScript | Всё | **Не защищаемся.** Фундаментальное ограничение веб-E2EE: код шифрования отдаёт тот же сервер. Описывается в README/SPEC честно |

Не цели: прямая секретность внутри одной сессии (Double Ratchet), защита от скомпрометированного браузера или устройства, сокрытие метаданных (кто, когда, сколько сообщений, размер в блоках), обнаружение обрезки хвоста истории.

## 2. Секреты и ключи

Все примитивы — WebCrypto, без внешних JS-библиотек. Метки домена: `"nullchat-e2ee-v1 <назначение>"` (UTF-8), далее `L(x)`.

| Обозначение | Что это | Где живёт |
|---|---|---|
| `invite_token` | Существующий одноразовый токен входа (32 байта hex) | Фрагмент ссылки; сервер видит при join |
| `S` | Секрет ссылки, 32 случайных байта, base64url | Фрагмент ссылки `k=`; у создателя — в `sessionStorage` только до входа гостя (нужен, чтобы показывать ссылку); гость его не сохраняет; **сервер не видит** |
| `P` | Необязательный пароль | Только в голове/вводе; в хранилище не попадает |
| `pw` | `PBKDF2-SHA256(NFC(P), salt = L("password") ‖ S, 600 000 итераций, 256 бит)` или пусто | Только в памяти на время create/join; дальше не хранится |
| `IKM` | `S ‖ [1 байт: есть ли пароль] ‖ pw` | Вычисляется |
| `K_title` | `HKDF-SHA256(IKM, salt = L("salt"), info = L("title"))` → AES-256-GCM | Вычисляется |
| `K_mac` | `HKDF(IKM, info = L("handshake"))` → HMAC-SHA256 | Вычисляется |
| `verifier` | `HMAC(HKDF(IKM, info = L("join")), L("join"))`, 32 байта | Отправляется на сервер при create (как `join_verifier`) и при join (как `join_proof`) |
| `room_salt` | `HKDF(IKM, info = L("room-salt"))` | Вычисляется |
| `(d_c, Q_c)`, `(d_g, Q_g)` | Эфемерные пары ECDH P-256 создателя и гостя | Закрытый — неизвлекаемый `CryptoKey` в IndexedDB (§8); открытый — на сервере |
| `K_msg` | `HKDF(ECDH(d_self, Q_peer), salt = room_salt, info = L("messages") ‖ Q_c ‖ Q_g)` → AES-256-GCM | Вычисляется у обоих после входа гостя |

Сервер хранит `SHA-256(join_verifier)` и сравнивает с `SHA-256(join_proof)` за постоянное время. Перебирать пароль по verifier сервер не может: в verifier зашит `S`, которого у него нет. Если утекли одновременно ссылка и база сервера, перебор пароля замедляет PBKDF2.

## 3. Ссылка-приглашение

```
https://host/#invite=<invite_token>&k=<S base64url>[&pw=1]
```

`pw=1` — только подсказка интерфейсу показать поле пароля; на безопасность не влияет. После входа адрес заменяется на `#room=<id>` через `history.replaceState`, секрет из адресной строки и текущей записи истории исчезает.

## 4. Протокол

### Создание комнаты

1. Клиент: `S`, при наличии пароля `pw`, производные ключи, пара `(d_c, Q_c)`.
2. `key_share = {public_key: Q_c, mac: HMAC(K_mac, L("share creator") ‖ Q_c)}`.
3. `encrypted_title = nonce ‖ AES-GCM(K_title, pad256(title), aad = L("title"))` — всегда ровно 284 байта (12 + 256 + 16), даже для пустого названия.
4. `POST /api/v1/rooms {"encrypted_title","ttl_minutes","key_share","join_verifier"}`.

### Вход гостя

1. Клиент читает `invite`, `k`, при `pw=1` спрашивает пароль, вычисляет `verifier`, пару `(d_g, Q_g)` и `key_share` с ролью `guest`.
2. `POST /api/v1/join {"invite_token","join_proof","key_share"}`.
3. Сервер под тем же mutex: приглашение существует → сравнить proof. Несовпадение: `403 join_proof_invalid`, приглашение **не** расходуется, счётчик неудач +1; на 5-й неудаче приглашение удаляется и в комнату публикуется `invite_revoked`. Совпадение: атомарно израсходовать приглашение и добавить гостя, как сейчас.

### Согласование ключа

- `participants[]` получают поля `role` (`creator`/`guest`, назначает сервер) и `key_share`.
- Каждый клиент при `snapshot`/`participants` проверяет MAC каждой доли с ролью из записи; свою долю — сравнением с собственным открытым ключом. Неудача → состояние «ключ не прошёл проверку», отправка запрещена навсегда, явное предупреждение.
- Когда обе доли проверены: `K_msg` и **код сверки** `SHA-256(L("safety") ‖ Q_c ‖ Q_g)` → три группы по 4 цифры (`uint32 mod 10000`). Код показывается в боковой панели; сверять голосом необязательно.
- До входа гостя общего ключа нет: поле ввода отключено с пояснением «Ждём собеседника».

### Сообщение

- Открытый текст: `0x01 ‖ counter (uint32 BE) ‖ prev (uint32 BE) ‖ UTF-8(text) ‖ 0x80 ‖ 0x00…` до кратного 256 байт (ISO/IEC 7816-4). Текст 1–4000 байт после trim → 256…4096 байт.
- `ciphertext = base64url(nonce(12) ‖ AES-GCM(K_msg, plaintext, aad))`, `aad = UTF-8(JSON.stringify(["nullchat-e2ee-v1 message", room_id, sender_id, client_message_id]))`.
- `counter` — счётчик отправителя с 1, назначается при шифровании; все отправки идут через одну очередь, поэтому счётчики уходят на сервер в порядке назначения. `prev` — счётчик последнего своего сообщения, которое сервер уже принял (по истории), или 0.
- Повтор неподтверждённого сообщения (потерян ack, обрыв) переиспользует тот же шифротекст, иначе новый nonce дал бы `message_id_conflict`. Сообщение, получившее явную ошибку или не ушедшее в сокет, сервер не сохранял: при «Повторить» оно шифруется заново с новым `client_message_id` и новым счётчиком, иначе старый счётчик после более новых выглядел бы как повтор.
- WS: `{"type":"send_message","client_message_id":"<UUID>","ciphertext":"…"}`; в `message`/`ack` поле `text` заменено на `ciphertext`.
- Получатель обходит историю в порядке `sequence`: если счётчик не больше уже виденного от этого отправителя — «повтор или перестановка», сообщение скрывается с предупреждением; если `prev` указывает на сообщение, которого нет в истории, — пометка «пропало сообщение, которое сервер уже принимал». Неудачные отправки не дают ложных тревог: на них `prev` не ссылается. Ошибка расшифровки — пузырь «Не удалось расшифровать».
- Пара открытых ключей, на которой выведен `K_msg`, запоминается в `sessionStorage`: если после reload сервер покажет другую долю или пропавшего участника — это ошибка проверки ключа.

## 5. Проверки сервера (формат, не содержимое)

Все бинарные поля — base64url без `=`, строгое (канонические хвостовые биты).

| Поле | Требование |
|---|---|
| `encrypted_title` | ровно 284 байта |
| `key_share.public_key` | 65 байт, первый `0x04` (несжатая точка P-256; валидность точки проверяет клиент) |
| `key_share.mac`, `join_verifier`, `join_proof` | 32 байта |
| `ciphertext` | 12 + 16 + n байт, n кратно 256, 256 ≤ n ≤ 4096 |

Дедупликация по `(participant_id, client_message_id)` сравнивает шифротексты. Новый код ошибки `join_proof_invalid` (403). Новое событие `invite_revoked` (`{}`). Сервер больше не обрезает и не проверяет текст и название и не подставляет название по умолчанию.

## 6. Интерфейс

- Создание: флажок «Защитить паролем» и поле пароля; подсказка «Сообщи пароль отдельно от ссылки».
- Вход: поле пароля при `pw=1`; ошибка `join_proof_invalid` — «Неверный пароль или повреждённая ссылка. После 5 неудачных попыток приглашение сгорит».
- Боковая панель: блок «Код сверки» до/после входа гостя; предупреждение при непроверенном ключе; уведомление `invite_revoked`.
- Пустое состояние у создателя: «Поделись приглашением. Писать можно после входа собеседника — тогда появится общий ключ».
- Футер и README: вместо «Без E2EE» — «Сквозное шифрование: сервер хранит только шифротекст».
- `crypto.subtle` есть только в secure context (HTTPS или localhost) — иначе явная ошибка на главной.

## 7. Совместимость и цена

- Протокол v1 меняется несовместимо (`text` → `ciphertext`, `title` → `encrypted_title`); демо хранит всё в памяти, миграции нет. Открытого режима больше нет.
- Худший объём истории: 500 × ~5,5 КБ base64 ≈ 2,7 МБ на комнату (было ≈ 2 МБ); WS-кадр отправки ≤ ~5,6 КБ при лимите 8192.
- `web/app.js` становится ES-модулем (`<script type="module">`), криптография — отдельный `web/crypto.js`, тестируется `node --test` без зависимостей; хранилище ключей — `web/keystore.js` (IndexedDB, только браузер); в CI добавляется Node.

## 8. Усиление веб-клиента

Главные угрозы веб-E2EE — XSS и подмена кода. Базовая защита уже есть: `textContent` вместо `innerHTML`, CSP `script-src 'self'`, ни одной внешней зависимости. Сверх неё:

1. **Trusted Types.** В CSP добавляется `require-trusted-types-for 'script'; trusted-types 'none'`. Браузер запрещает присваивать строки в `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, а также `eval` и строковый `setTimeout`. Политик нет совсем, так что даже ошибочно добавленный вызов просто не сработает. Браузеры без поддержки игнорируют директиву, и для них остаются прежние меры.
2. **Неизвлекаемые ключи.** Закрытый ECDH-ключ создаётся с `extractable: false`, `K_title` и `K_mac` тоже неизвлекаемые. Ключи вместе с `room_salt` хранятся в IndexedDB (`nullchat` → `keys`, ключ записи `<room_id>:<participant_id>`, плюс `expires_ms` — срок числом, чтобы неразобранная дата никогда не выглядела истёкшей). Скрипт, попавший на страницу, может пользоваться ключами, пока открыта вкладка, но не может их скопировать. В `sessionStorage` остаются только токен сессии, открытый ключ, счётчик, флаг пароля и, у создателя до входа гостя, `S`. Запись удаляется при `room_closed`/`room_expired`/`session_invalid`; при каждом открытии страницы просроченные записи вычищаются. Цена: IndexedDB общий для origin и переживает закрытие вкладки, поэтому ключи могут пролежать на диске до следующего визита или до конца TTL. Без шифротекста они бесполезны, а сервер стирает историю вместе с комнатой. Если IndexedDB недоступен, ключи живут только в памяти, и интерфейс предупреждает, что после обновления вкладки сессия не восстановится.
3. **Изоляционные заголовки.** `Cross-Origin-Opener-Policy: same-origin` (чужая вкладка не получает `window.opener`), `Cross-Origin-Resource-Policy: same-origin` (ресурсы не встраиваются чужими сайтами), `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), browsing-topics=()`. К уже существующим `frame-ancestors 'none'`, `nosniff`, `no-referrer`.
4. **Опубликованный хеш фронтенда.** `go run ./cmd/webhash` печатает SHA-256 каждого встроенного файла `web/` и общий хеш манифеста. CI печатает его в лог, README объясняет, как сверить развёрнутый сервис: `curl -s https://host/app.js | sha256sum`. Это обнаружение подмены задним числом, а не её предотвращение: страница, которую уже отдал сервер, сама себя проверить не может. SRI не используется — хеш, отданный тем же сервером, ничего не доказывает.

## 9. Тесты

- Go (`internal/chat`): валидация форматов; неверный proof не расходует приглашение; 5 неудач → `invite_revoked` и `room_unavailable`; конкурентный вход с верным proof — ровно один гость; дедупликация и конфликт по шифротексту; существующие инварианты (snapshot без разрыва, TTL, End, медленный подписчик) на новых входных данных.
- Go (`internal/httpapi`): таблица валидации, 403 `join_proof_invalid`, интеграционный WS-тест с шифротекстом, CSP с Trusted Types и изоляционные заголовки на каждом ответе.
- Go (`web`): манифест хешей покрывает все встроенные файлы и стабилен.
- Node (`web/crypto.test.mjs`): base64url, pad/unpad, одинаковые `K_msg` и код сверки у обеих сторон, отказ при чужой роли/подмене ключа, закрытый ключ неизвлекаем, подмене AAD, разные verifier с паролем и без, фиксированные размеры шифротекстов, совпадающие с серверными проверками, `checkCounters` (повтор, перестановка, удалённое принятое сообщение, отсутствие тревог для неудачных отправок); размеры берутся из констант `envelope.go`, поэтому расхождение Go и JS роняет тест.
- Ручной браузерный smoke: два контекста, с паролем и без, reload (ключи берутся из IndexedDB), неверный пароль, очистка IndexedDB после завершения, отсутствие нарушений Trusted Types в консоли, перехваченный ключ (ручная подмена доли).
