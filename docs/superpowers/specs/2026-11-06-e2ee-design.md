# Design: end-to-end encryption (E2EE) in nullchat

Status: agreed in discussion on 2026-11-06, implemented per the [plan](../plans/2026-11-06-e2ee.md). E2EE is added at direct request, outside the main step sequence of `docs/PLAN.md`; this is recorded as a separate Decision 006 in `docs/ARCHITECTURE.md`.

## 1. Goal and threat model

The server (and anything that sees its memory, disk or traffic behind TLS) must not learn the message text or the room title, must not silently substitute the participants' keys and must not silently reorder, replay or forge messages.

| Adversary | What they get | Outcome |
|---|---|---|
| Server / operator, passive | Ciphertexts, public ECDH keys, verifier | Cannot read the conversation or the title; length is hidden to 256-byte blocks |
| Server, active (key substitution) | — | Cannot sign someone else's key without the link secret; a substitution breaks the exchange and changes the safety code |
| Server substitutes/replays/reorders messages | — | A substitution breaks the AES-GCM tag; replay and reordering are visible from the sender's counter |
| Link interceptor without the password | The link | Can join in place of the guest (the guest will see "invite already used"); with a password, cannot join |
| Link and password leak after the conversation | Link, password | Does not expose the conversation: the message key is derived from ephemeral ECDH, the private keys lived only in the tabs |
| Server substitutes the JavaScript | Everything | **No protection.** A fundamental limitation of web E2EE: the encryption code is served by the same server. Described honestly in README/SPEC |

Non-goals: forward secrecy within a single session (Double Ratchet), protection against a compromised browser or device, metadata hiding (who, when, how many messages, size in blocks), detection of history tail truncation.

## 2. Secrets and keys

All primitives are WebCrypto, with no external JS libraries. Domain labels: `"nullchat-e2ee-v1 <purpose>"` (UTF-8), written `L(x)` below.

| Symbol | What it is | Where it lives |
|---|---|---|
| `invite_token` | The existing one-time join token (32 bytes hex) | Link fragment; the server sees it on join |
| `S` | Link secret, 32 random bytes, base64url | Link fragment `k=`; for the creator, in `sessionStorage` only until the guest joins (needed to show the link); the guest does not store it; **the server does not see it** |
| `P` | Optional password | Only in the user's head/input; never reaches storage |
| `pw` | `PBKDF2-SHA256(NFC(P), salt = L("password") ‖ S, 600 000 iterations, 256 bits)` or empty | Only in memory during create/join; not stored afterwards |
| `IKM` | `S ‖ [1 byte: whether there is a password] ‖ pw` | Computed |
| `K_title` | `HKDF-SHA256(IKM, salt = L("salt"), info = L("title"))` → AES-256-GCM | Computed |
| `K_mac` | `HKDF(IKM, info = L("handshake"))` → HMAC-SHA256 | Computed |
| `verifier` | `HMAC(HKDF(IKM, info = L("join")), L("join"))`, 32 bytes | Sent to the server on create (as `join_verifier`) and on join (as `join_proof`) |
| `room_salt` | `HKDF(IKM, info = L("room-salt"))` | Computed |
| `(d_c, Q_c)`, `(d_g, Q_g)` | Ephemeral ECDH P-256 pairs of the creator and the guest | Private: a non-extractable `CryptoKey` in IndexedDB (§8); public: on the server |
| `K_msg` | `HKDF(ECDH(d_self, Q_peer), salt = room_salt, info = L("messages") ‖ Q_c ‖ Q_g)` → AES-256-GCM | Computed by both after the guest joins |

The server stores `SHA-256(join_verifier)` and compares it with `SHA-256(join_proof)` in constant time. The server cannot brute-force the password from the verifier: the verifier includes `S`, which the server does not have. If the link and the server database leak together, PBKDF2 slows down password brute-forcing.

## 3. Invite link

```
https://host/#invite=<invite_token>&k=<S base64url>[&pw=1]
```

`pw=1` is only a hint for the interface to show the password field; it does not affect security. After joining, the address is replaced with `#room=<id>` via `history.replaceState`, and the secret disappears from the address bar and the current history entry.

## 4. Protocol

### Room creation

1. Client: `S`, `pw` if there is a password, derived keys, the pair `(d_c, Q_c)`.
2. `key_share = {public_key: Q_c, mac: HMAC(K_mac, L("share creator") ‖ Q_c)}`.
3. `encrypted_title = nonce ‖ AES-GCM(K_title, pad256(title), aad = L("title"))`: always exactly 284 bytes (12 + 256 + 16), even for an empty title.
4. `POST /api/v1/rooms {"encrypted_title","ttl_minutes","key_share","join_verifier"}`.

### Guest join

1. The client reads `invite`, `k`, asks for the password if `pw=1`, computes `verifier`, the pair `(d_g, Q_g)` and a `key_share` with the role `guest`.
2. `POST /api/v1/join {"invite_token","join_proof","key_share"}`.
3. The server, under the same mutex: the invite exists → compare the proof. Mismatch: `403 join_proof_invalid`, the invite is **not** consumed, the failure counter +1; on the 5th failure the invite is deleted and `invite_revoked` is published to the room. Match: atomically consume the invite and add the guest, as now.

### Key agreement

- `participants[]` get the fields `role` (`creator`/`guest`, assigned by the server) and `key_share`.
- On `snapshot`/`participants`, each client verifies the MAC of every share with the role from the record; its own share by comparing with its own public key. Failure → the "key verification failed" state, sending is forbidden permanently, an explicit warning.
- Once both shares are verified: `K_msg` and the **safety code** `SHA-256(L("safety") ‖ Q_c ‖ Q_g)` → three groups of 4 digits (`uint32 mod 10000`). The code is shown in the sidebar; comparing it by voice is optional.
- Before the guest joins there is no shared key: the input field is disabled with the explanation "Waiting for your contact".

### Message

- Plaintext: `0x01 ‖ counter (uint32 BE) ‖ prev (uint32 BE) ‖ UTF-8(text) ‖ 0x80 ‖ 0x00…` up to a multiple of 256 bytes (ISO/IEC 7816-4). Text of 1–4000 bytes after trim → 256…4096 bytes.
- `ciphertext = base64url(nonce(12) ‖ AES-GCM(K_msg, plaintext, aad))`, `aad = UTF-8(JSON.stringify(["nullchat-e2ee-v1 message", room_id, sender_id, client_message_id]))`.
- `counter` is the sender's counter starting at 1, assigned at encryption; all sends go through one queue, so the counters reach the server in the order assigned. `prev` is the counter of the sender's last own message the server has already accepted (per the history), or 0.
- Retrying an unacknowledged message (lost ack, connection drop) reuses the same ciphertext, otherwise a new nonce would produce `message_id_conflict`. A message that got an explicit error or never reached the socket was not stored by the server: on "Retry" it is re-encrypted with a new `client_message_id` and a new counter, otherwise the old counter after newer ones would look like a replay.
- WS: `{"type":"send_message","client_message_id":"<UUID>","ciphertext":"…"}`; in `message`/`ack` the `text` field is replaced with `ciphertext`.
- The recipient walks the history in `sequence` order: if the counter is not greater than the one already seen from this sender, it is a "replay or reorder", and the message is hidden with a warning; if `prev` points to a message missing from the history, it is flagged "A message the server had already accepted is missing". Failed sends cause no false alarms: `prev` does not reference them. A decryption error shows a bubble "This message could not be decrypted".
- The pair of public keys `K_msg` was derived from is remembered in `sessionStorage`: if after a reload the server shows a different share or a missing participant, it is a key verification error.

## 5. Server checks (shape, not content)

All binary fields are base64url without `=`, strict (canonical trailing bits).

| Field | Requirement |
|---|---|
| `encrypted_title` | exactly 284 bytes |
| `key_share.public_key` | 65 bytes, first byte `0x04` (uncompressed P-256 point; the client checks point validity) |
| `key_share.mac`, `join_verifier`, `join_proof` | 32 bytes |
| `ciphertext` | 12 + 16 + n bytes, n a multiple of 256, 256 ≤ n ≤ 4096 |

Deduplication by `(participant_id, client_message_id)` compares ciphertexts. New error code `join_proof_invalid` (403). New event `invite_revoked` (`{}`). The server no longer trims or validates the text and the title and no longer substitutes a default title.

## 6. Interface

- Creation: a "Protect with a password" checkbox and a password field; the hint "share it separately from the link".
- Join: a password field when `pw=1`; the `join_proof_invalid` error reads "Wrong password or damaged link. After 5 failed attempts the invite is revoked."
- Sidebar: a "Safety code" block before/after the guest joins; a warning on an unverified key; an `invite_revoked` notice.
- Empty state for the creator: "Share the invite. You can write once your contact joins: that is when the shared key appears."
- Footer and README: instead of "No E2EE", "End-to-end encrypted: the server sees only ciphertext.".
- `crypto.subtle` exists only in a secure context (HTTPS or localhost); otherwise an explicit error on the home page.

## 7. Compatibility and cost

- Protocol v1 changes incompatibly (`text` → `ciphertext`, `title` → `encrypted_title`); the demo keeps everything in memory, there is no migration. There is no plaintext mode anymore.
- Worst-case history size: 500 × ~5.5 KB base64 ≈ 2.7 MB per room (was ≈ 2 MB); a send WS frame is ≤ ~5.6 KB against a limit of 8192.
- `web/app.js` becomes an ES module (`<script type="module">`), cryptography is a separate `web/crypto.js`, tested with `node --test` without dependencies; the key store is `web/keystore.js` (IndexedDB, browser only); Node is added to CI.

## 8. Web client hardening

The main threats to web E2EE are XSS and code substitution. The baseline protection already exists: `textContent` instead of `innerHTML`, CSP `script-src 'self'`, not a single external dependency. On top of that:

1. **Trusted Types.** The CSP gets `require-trusted-types-for 'script'; trusted-types 'none'`. The browser forbids assigning strings to `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, as well as `eval` and string `setTimeout`. There are no policies at all, so even a mistakenly added call simply will not work. Browsers without support ignore the directive, and the earlier measures remain for them.
2. **Non-extractable keys.** The private ECDH key is created with `extractable: false`, `K_title` and `K_mac` are non-extractable too. The keys together with `room_salt` are stored in IndexedDB (`nullchat` → `keys`, record key `<room_id>:<participant_id>`, plus `expires_ms`, the expiry as a number, so that an unparsed date never looks expired). A script injected into the page can use the keys while the tab is open but cannot copy them. `sessionStorage` keeps only the session token, the public key, the counter, the password flag and, for the creator until the guest joins, `S`. The record is deleted on `room_closed`/`room_expired`/`session_invalid`; expired records are purged on every page open. The cost: IndexedDB is shared across the origin and survives closing the tab, so keys may stay on disk until the next visit or the end of the TTL. Without the ciphertext they are useless, and the server erases the history together with the room. If IndexedDB is unavailable, the keys live only in memory, and the interface warns that the session will not be restored after reloading the tab.
3. **Isolation headers.** `Cross-Origin-Opener-Policy: same-origin` (a foreign tab does not get `window.opener`), `Cross-Origin-Resource-Policy: same-origin` (resources are not embedded by foreign sites), `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), browsing-topics=()`. In addition to the existing `frame-ancestors 'none'`, `nosniff`, `no-referrer`.
4. **Published frontend hash.** `go run ./cmd/webhash` prints the SHA-256 of each embedded `web/` file and an overall manifest hash. CI prints it to the log, and the README explains how to verify the deployed service: `curl -s https://host/app.js | sha256sum`. This detects substitution after the fact rather than preventing it: a page the server has already served cannot verify itself. SRI is not used: a hash served by the same server proves nothing.

## 9. Tests

- Go (`internal/chat`): format validation; a wrong proof does not consume the invite; 5 failures → `invite_revoked` and `room_unavailable`; a concurrent join with a correct proof yields exactly one guest; deduplication and conflict by ciphertext; the existing invariants (snapshot without a gap, TTL, End, slow subscriber) on the new inputs.
- Go (`internal/httpapi`): a validation table, 403 `join_proof_invalid`, an integration WS test with ciphertext, CSP with Trusted Types and isolation headers on every response.
- Go (`web`): the hash manifest covers all embedded files and is stable.
- Node (`web/crypto.test.mjs`): base64url, pad/unpad, identical `K_msg` and safety code on both sides, rejection on a wrong role/key substitution, the private key is non-extractable, AAD substitution, different verifiers with and without a password, fixed ciphertext sizes matching the server checks, `checkCounters` (replay, reorder, a deleted accepted message, no alarms for failed sends); the sizes are taken from the `envelope.go` constants, so a Go/JS mismatch fails the test.
- Manual browser smoke test: two contexts, with and without a password, reload (keys come from IndexedDB), a wrong password, IndexedDB cleanup after ending, no Trusted Types violations in the console, an intercepted key (manual share substitution).
