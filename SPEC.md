# Техническое задание: nullchat

Статус: реализована PostgreSQL-основа версии 0.2; outbox/replay, paging и несколько сервисов отложены. Обновлено 06.11.2026 (сквозное шифрование). Этот документ заменяет исходное ТЗ шлюза к Matrix. Выполненные проверки и их ограничения перечислены в [VERIFICATION.md](docs/VERIFICATION.md); полный roadmap 0.2 ещё не завершён.

## 1. Цель

Создать временный чат без регистрации как Go-проект для портфолио. Пользователь создаёт комнату на двоих, передаёт приглашение и общается до истечения TTL. Продемонстрировать конкурентную работу, реальные сетевые соединения, явные гарантии доставки, тестирование и понятную архитектуру.

Matrix, федерация, аккаунты, файлы, звонки, группы, typing и read receipts не входят в демо. Сообщения и название комнаты шифруются в браузере (E2EE, решение 006 в [архитектуре](docs/ARCHITECTURE.md), подробности — в [дизайне](docs/superpowers/specs/2026-11-06-e2ee-design.md)). Два микросервиса рассматриваются после работающей версии с PostgreSQL.

## 2. Пользовательский сценарий

1. Создатель указывает необязательное название (до 60 Unicode-символов), TTL 1–60 минут (по умолчанию 30) и при желании пароль. Браузер создаёт секрет ссылки и эфемерную пару ECDH, шифрует название и отправляет серверу только шифротекст, подписанный открытый ключ и verifier входа.
2. Сервер создаёт комнату, сессию создателя и одноразовый токен приглашения гостя. Для каждого участника backend генерирует случайное английское display name; имя уникально внутри комнаты, а внутренние идентификаторы случайные.
3. Приглашение имеет вид `https://host/#invite=<token>&k=<секрет>[&pw=1]`. Фрагмент не отправляется в HTTP-запросе страницы, поэтому секрет `k` сервер не видит. `pw=1` показывает поле пароля. Открытие страницы не занимает место: гость нажимает «Войти».
4. Гость отправляет `join_proof`, вычисленный из секрета ссылки и пароля. Сервер сравнивает его с verifier: при несовпадении возвращает `join_proof_invalid` и не расходует приглашение; после 5 неудач приглашение аннулируется (`invite_revoked`). Успешный вход атомарно использует приглашение и выдаёт отдельную сессию. Одновременные входы не могут создать третьего участника.
5. После входа гостя оба браузера проверяют подписи открытых ключей, выводят общий ключ сообщений и показывают одинаковый код сверки. До этого писать нельзя: общего ключа ещё нет. Оба участника получают историю и новые сообщения через WebSocket.
6. Обновление страницы сохраняет сессию в пределах вкладки. При сетевом обрыве интерфейс переподключается с задержкой 1–10 секунд.
7. Любой участник может завершить чат для обоих. По TTL происходит то же самое автоматически.

## 3. Жизненный цикл

- TTL начинается при создании, не продлевается активностью и проверяется сервером.
- После `expires_at` вход, подписка и отправка запрещены независимо от фонового очистителя.
- Очиститель проверяет комнаты раз в секунду. Онлайн-клиент получает `room_expired`; доставка уведомления зависит от сети.
- `room_closed` означает явное завершение любым участником.
- Сессии и приглашения комнаты отзываются, история становится недоступна через API; expiry worker удаляет истёкшие строки идемпотентности, а остальные строки PostgreSQL сохраняются до отдельно реализуемой физической очистки.
- Закрытие вкладки не считается надёжным сигналом выхода и не освобождает место гостя. Сессия действительна до закрытия комнаты.
- В текущем runtime с PostgreSQL рестарт backend разрывает WebSocket-соединения, но не закрывает активную комнату и не отзывает действующие сессии. Клиент может переподключиться с прежней сессией до `expires_at` или явного завершения комнаты.
- Остановка приложения и завершение разговора — разные операции: graceful shutdown не отправляет `room_closed` и не удаляет комнату из постоянного хранилища.

## 4. HTTP API v1

Ответы — JSON, ошибки имеют вид `{"error":"code"}`. Все ответы имеют `Cache-Control: no-store, no-transform`.

| Метод и путь | Запрос | Результат |
|---|---|---|
| `POST /api/v1/rooms` | `{"encrypted_title":"…", "ttl_minutes":30, "key_share":{"public_key":"…","mac":"…"}, "join_verifier":"…"}` | `201`, room, self, session_token, invite_token |
| `POST /api/v1/join` | `{"invite_token":"…", "join_proof":"…", "key_share":{…}}` | `200`, room, self, session_token |
| `POST /api/v1/end` | Заголовок `Authorization: Bearer <session_token>` | `200`, `{"ok":true}`; закрывает комнату |
| `GET /ws` | WebSocket upgrade, затем authenticate | Поток событий |
| `GET /healthz` | — | `200`, `{"status":"ok"}` |
| `GET /readyz` | — | `200`, `{"status":"ready"}` при успешном ping БД; иначе `503 database_unavailable` |

`room` содержит `id`, `encrypted_title`, `expires_at`, `participants`, `messages`. Участник (`self` и элементы `participants`) содержит `id`, `name`, `role` (`creator`/`guest`) и `key_share`.

Бинарные поля — base64url без `=` (строгое кодирование). Сервер проверяет только форму: `encrypted_title` — ровно 284 байта; `key_share.public_key` — 65 байт, начинается с `0x04`; `key_share.mac`, `join_verifier`, `join_proof` — 32 байта; `ciphertext` — 12 + 16 + n байт, где n кратно 256 и 256 ≤ n ≤ 4096.

Create/join принимают необязательный `Idempotency-Key`: 32–128 печатных ASCII-символов. Клиент генерирует случайный ключ и сохраняет его для повтора того же запроса. Отпечаток включает endpoint и все поля запроса, включая шифротекст названия, долю ключа и verifier/proof. Поэтому клиент шифрует запрос один раз и при повторе отправляет его без изменений. Replay credentials зашифрован AES-GCM; один ключ с другим endpoint/отпечатком получает `409 idempotency_key_conflict`. После end/TTL replay получает `410 room_unavailable`.

`/healthz` не обращается к БД. `/readyz` проверяет ping, а не версию схемы: миграции выполняются отдельно (`cmd/migrate`) или при старте с `MIGRATE_ON_START=true` для хостингов без pre-deploy шага.

Основные ошибки: `invalid_input` (400), `session_invalid` (401), `origin_forbidden` и `join_proof_invalid` (403), `room_unavailable` (410), `message_id_conflict` и `idempotency_key_conflict` (409), `rate_limited` и `capacity_reached` (429), `database_unavailable` (503). Недоступные/использованные приглашения не раскрывают подробности комнаты.

Лимиты различаются по причине: `room_full` — в комнате уже два участника; `message_limit` — достигнут лимит сообщений комнаты; `connection_limit` — исчерпан лимит WebSocket/подписок; `rate_limited` — превышена частота запросов или команд; `database_unavailable` — хранилище не готово. Клиент должен понимать, что можно повторить, а что требует другого действия.

## 5. WebSocket-протокол

Сначала, в течение пяти секунд после upgrade:

```json
{"type":"authenticate","session_token":"<64 hex characters>"}
```

Сессионный токен не передаётся в URL. После аутентификации сервер присылает `snapshot` с `payload: {room, self}`. Снимок истории и подключение к потоку выполняются атомарно.

Отправка:

```json
{"type":"send_message","client_message_id":"<UUID>","ciphertext":"<base64url>"}
```

Сообщение сервера:

```json
{
  "type": "message",
  "payload": {
    "sequence": 1,
    "id": "<server ID>",
    "client_message_id": "<UUID>",
    "sender_id": "<participant ID>",
    "ciphertext": "<base64url>",
    "created_at": "2026-09-20T12:00:00Z"
  }
}
```

| Событие | Payload / назначение |
|---|---|
| `snapshot` | `{room, self}` — состояние после подключения |
| `message` | Сообщение — получают оба участника |
| `ack` | То же сообщение — подтверждение приёма отправителю |
| `participants` | Массив участников с долями ключа после входа гостя; не индикатор online |
| `invite_revoked` | `{}` — приглашение аннулировано после 5 неверных `join_proof` |
| `error` | `{code, client_message_id?}` |
| `room_expired` | `{}` — TTL истёк |
| `room_closed` | `{}` — чат завершён участником |
| `server_shutdown` | `{}` — сервер останавливается; отправляется перед close `1001`, браузер сохраняет сессию и переподключается |

### Реализованные гарантии

- `ack` возвращается только после успешного commit сообщения в PostgreSQL. Это не подтверждение прочтения или доставки собеседнику.
- Повтор `(participant_id, client_message_id)` с тем же шифротекстом возвращает прежний результат. С другим шифротекстом — `message_id_conflict`. Клиент повторяет отправку тем же шифротекстом, а не шифрует заново.
- Каждое новое сообщение получает возрастающий `sequence` внутри комнаты. UI сортирует по нему и убирает дубликаты по `id`; `ack` и `message` могут приходить в разном порядке.
- При переподключении вся история комнаты заменяет локальный снимок. Неподтверждённые сообщения открытой страницы отправляются повторно с прежними ID.
- Клиент обрезает текст по краям; он не должен быть пустым и должен занимать не более 4000 байт UTF-8. Открытый текст `0x01 ‖ counter (uint32) ‖ prev (uint32) ‖ текст` дополняется до кратного 256 байт и шифруется AES-256-GCM; в AAD входят room, sender и `client_message_id`. `counter` растёт в порядке отправки, `prev` — последнее своё сообщение, уже принятое сервером. Получатель скрывает с предупреждением повтор или перестановку и помечает сообщение, если пропало принятое ранее. Неудачная отправка при «Повторить» шифруется заново с новым `client_message_id`.
- Гарантия exactly-once по сети не заявляется. Комнаты, сессии и подтверждённая история переживают рестарт backend при сохранной БД. Hub событий остаётся в памяти: durable outbox/replay отсутствуют. Сбой после commit до broadcast восстанавливается снимком при reconnect; остающийся подключённым клиент может пропустить событие.

### Реализованная PostgreSQL-основа версии 0.2

Эти свойства покрывают PostgreSQL integration tests: `TestOperationsCommitFailureDoesNotPublish`, `TestServerRestartPreservesCommittedRoom`, `TestCommittedRoomSurvivesServiceRestart`, `TestConcurrentIdempotencyFirstUse`, `TestExpireDeletesExpiredIdempotencyAndAllowsKeyReuse`, тесты replay/conflict create/join и отзыва доступа. Они не означают завершения outbox, paging, полной очистки истории или всех UI-состояний roadmap.

- `ack` означает, что сообщение принято и успешно зафиксировано PostgreSQL (`commit`). Это не подтверждение доставки собеседнику или прочтения. Фактическая durability зависит от настроек PostgreSQL, включая режим подтверждения записи и работу диска/репликации.
- Повтор отправки с тем же `(room_id, participant_id, client_message_id)` и тем же шифротекстом возвращает исходное принятое сообщение. Другая нагрузка с тем же ключом получает `message_id_conflict`.
- После потери HTTP-ответа повтор `create` или `join` с тем же ключом идемпотентности и тем же отпечатком запроса возвращает исходный результат в пределах окна повтора. Другой запрос с тем же ключом получает `idempotency_key_conflict`. После окончания окна повтор не гарантируется.
- Потеря WebSocket или рестарт backend не закрывают комнату и не отзывают сессию. После восстановления клиент получает актуальное состояние и продолжает работу с прежним токеном, если TTL не истёк и участник не завершил комнату.
- При истечении TTL или явном завершении доступ отзывается окончательно: поздние отправки и повторное подключение получают `session_invalid` либо `room_unavailable` согласно HTTP/WebSocket-контракту; действующий токен не восстанавливает доступ.

## 6. Состояния интерфейса (целевой полный контракт)

Реализовано сохранение сессии при `server_shutdown` и повторяемых временных ошибках (включая закрытие WS с кодом `1013`). Полный redesign failed/pending и отдельного отображения unavailable ещё отложен; этот раздел не является отчётом о выполнении всех UI-требований.

Клиент явно отображает одно из следующих состояний:

- `connecting` — устанавливается первое WebSocket-соединение;
- `connected` — сессия подтверждена, поток событий активен;
- `reconnecting` — временный сетевой или серверный сбой, сессия сохраняется и выполняются ограниченные повторы;
- `expired` — TTL истёк, доступ отозван окончательно;
- `closed` — участник завершил комнату, доступ отозван окончательно;
- `unavailable` — сервер или база временно недоступны, повтор возможен без удаления действующей сессии.

`reconnecting` и `unavailable` не означают истечение сессии. `expired`, `closed` и недействительный токен означают окончательную потерю доступа. Неотправленный текст и неудачное сообщение должны иметь отдельное состояние ошибки и не исчезать из интерфейса автоматически.

## 7. Ограничения и приватность

Сводка наблюдателей и того, что каждый видит, — в [SECURITY.md](docs/SECURITY.md).

- Токены: 32 криптографически случайных байта; серверные индексы хранят SHA-256 токенов. В `idempotency_requests` credentials доступны только в зашифрованном AES-GCM ответе; deployment key хранится вне репозитория и сохраняется между рестартами.
- `sessionStorage` хранит токен сессии, открытый ключ, счётчик сообщений и (у создателя до входа гостя) секрет ссылки; история, пароль и закрытые ключи туда не сохраняются. Закрытый ECDH-ключ и производные ключи — неизвлекаемые `CryptoKey` в IndexedDB; запись удаляется при завершении комнаты, просроченные записи вычищаются при открытии страницы.
- WebSocket и API проверяют Origin по host. Запросы без Origin разрешены для небраузерных клиентов; Origin не заменяет аутентификацию.
- Сжатие WebSocket (`permessage-deflate`) и HTTP-ответов в приложении выключено явно, а `Cache-Control: no-store, no-transform` запрещает его прокси и CDN: длина ответа не должна зависеть от совпадения данных атакующего с секретами (CRIME/BREACH). Лог ошибок `net/http` проходит фильтр, который заменяет адреса клиентов на `<addr>`.
- CSP с Trusted Types (`require-trusted-types-for 'script'; trusted-types 'none'`), `textContent` вместо вставки HTML сообщений, отсутствие внешних скриптов, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy` и `Cross-Origin-Resource-Policy: same-origin`, `Permissions-Policy` без камеры, микрофона и геолокации. `go run ./cmd/webhash` печатает SHA-256 встроенных файлов для сверки развёрнутого фронтенда.
- Реализованные лимиты: 100 активных комнат, 500 сообщений на комнату; 400 сокетов суммарно и 2 на одну сессию для короткого перекрытия при reconnect. Раздельные бюджеты create/join/upgrade остаются целевым требованием.
- Хранение сейчас: end/TTL меняют статус и отзывают доступ; expiry worker удаляет `idempotency_requests` после их собственного `expires_at`, позволяя повторно использовать ключ как новый. Физическая очистка остальных строк комнаты не реализована; в них лежат только шифротексты, доли ключей и SHA-256 verifier. Миграция `0003_e2ee` закрыла комнаты, созданные до E2EE, и удалила их открытые сообщения и названия. Цель retention истории — TTL комнаты плюс 24 часа — остаётся отложенной, а не гарантией удаления. Durable event store отсутствует. Политики WAL/backup и удаления из основной БД требуют отдельной реализации; мгновенное физическое стирание не обещается.
- Результат `create`/`join` для идемпотентного повтора доступен до окончания комнаты, но не более 24 часов после исходного запроса; после этого повтор не гарантируется. Открытые session/invite токены не хранятся в логах.
- Текущий общий бюджет создания/входа/upgrade: 120 запросов в минуту на процесс. Разделение квот восстановления сессий и создания комнат отложено. Новые сообщения одной сессии — не чаще одного в 200 мс. Общие лимиты не заменяют защиту публичного сервиса от злоупотреблений.
- Очередь подписчика — 64 события; переполненный подписчик отсоединяется от потока, затем сокет закрывается и клиент восстанавливает историю. Сетевые записи имеют timeout 5 секунд.
- Ping раз в 25 секунд, timeout ответа 5 секунд; WebSocket-фреймы приложения не более 8192 байт.
- Прикладные логи содержат запуск, остановку и системные ошибки. Тексты, токены, IP и User-Agent не пишутся прикладным кодом; стандартный HTTP-сервер может журналировать аварийные ошибки. Публичное развёртывание требует отдельной проверки журналов proxy/runtime.
- HTTPS обязателен вне localhost (WebCrypto работает только в secure context). Backend не видит текст сообщений и название: только шифротекст, размер с точностью до 256 байт, время, участников и открытые ключи. Сервер не может подменить ключи без секрета ссылки (и пароля) — подмена обнаруживается проверкой подписи и кодом сверки. Ограничения: веб-E2EE доверяет JavaScript, который отдаёт сервер, — скомпрометированный сервер может отдать изменённый код; тот, кто перехватил ссылку без пароля, может войти вместо гостя (гость увидит, что приглашение использовано); обрезку хвоста истории клиент не обнаруживает. Не обещаются полная анонимность или физическое стирание памяти.

## 8. Критерии приёмки текущего монолита

- Запуск по README с PostgreSQL 17, явной миграцией и секретом окружения; без Matrix и frontend toolchain. Go 1.25+ для сборки на хосте.
- Два независимых браузерных контекста обмениваются сообщениями.
- Одноразовый вход и лимит двух участников выдерживают конкурентные запросы.
- Повтор сообщения не дублирует историю.
- Reload/reconnect восстанавливает текущую комнату и историю.
- TTL и явное завершение отзывают обе сессии.
- Медленный подписчик не блокирует остальных.
- Сервер не получает открытого текста сообщений и названия; коды сверки у обоих участников совпадают; неверный пароль не занимает место.
- Проходят `go test -race ./...`, `go vet ./...` и `node --test web/crypto.test.mjs`.
- README честно описывает ограничения демо и запуск.

## 9. Критерии приёмки версии 0.2

- Перезапуск backend не закрывает активную комнату: после восстановления сервиса оба участника могут переподключиться с прежними сессиями до TTL.
- `ack` выдаётся только после commit сообщения в PostgreSQL; искусственный сбой до commit не оставляет сообщение, а сбой после commit допускает безопасный повтор по прежнему `client_message_id`.
- Временная недоступность сети/БД не переводит действующую сессию в окончательно отозванное состояние.
- Для заполненной комнаты, лимита сообщений, лимита соединений, частого запроса и недоступной БД возвращаются разные стабильные коды.
- Повтор create/join после потери ответа не создаёт вторую комнату или участника в пределах согласованного окна идемпотентности.
