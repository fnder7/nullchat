# Техническое задание: nullchat

Статус: согласованное направление и реализованное демо. Обновлено 20.09.2026. Этот документ заменяет исходное ТЗ шлюза к Matrix.

## 1. Цель

Создать временный чат без регистрации как Go-проект для портфолио. Пользователь создаёт комнату на двоих, передаёт приглашение и общается до истечения TTL. Продемонстрировать конкурентную работу, реальные сетевые соединения, явные гарантии доставки, тестирование и понятную архитектуру.

Matrix, федерация, аккаунты, файлы, звонки, E2EE, группы, typing и read receipts не входят в демо. Два микросервиса рассматриваются после работающей версии с PostgreSQL.

## 2. Пользовательский сценарий

1. Создатель указывает необязательное название (до 60 Unicode-символов) и TTL 1–60 минут, по умолчанию 30.
2. Сервер создаёт комнату, сессию создателя и одноразовый токен приглашения гостя. Для каждого участника backend генерирует случайное английское display name; имя уникально внутри комнаты, а внутренние идентификаторы случайные.
3. Приглашение имеет вид `https://host/#invite=<token>`. Фрагмент не отправляется в HTTP-запросе страницы. Открытие страницы не занимает место: гость нажимает «Войти».
4. Успешный вход атомарно использует приглашение и выдаёт отдельную сессию. Одновременные входы не могут создать третьего участника.
5. Оба участника получают историю и новые сообщения через WebSocket. Гость видит и сообщения, отправленные до его входа.
6. Обновление страницы сохраняет сессию в пределах вкладки. При сетевом обрыве интерфейс переподключается с задержкой 1–10 секунд.
7. Любой участник может завершить чат для обоих. По TTL происходит то же самое автоматически.

## 3. Жизненный цикл

- TTL начинается при создании, не продлевается активностью и проверяется сервером.
- После `expires_at` вход, подписка и отправка запрещены независимо от фонового очистителя.
- Очиститель проверяет комнаты раз в секунду. Онлайн-клиент получает `room_expired`; доставка уведомления зависит от сети.
- `room_closed` означает явное завершение любым участником.
- Сессии и приглашения комнаты отзываются, история убирается из доступных структур сервера.
- Закрытие вкладки не считается надёжным сигналом выхода и не освобождает место гостя. Сессия действительна до закрытия комнаты.
- В текущем демо при рестарте процесса все комнаты исчезают. Это ограничение не является целевым контрактом следующей версии.
- В версии 0.2 с PostgreSQL рестарт backend разрывает WebSocket-соединения, но не закрывает активную комнату и не отзывает действующие сессии. Клиент может переподключиться с прежней сессией до `expires_at` или явного завершения комнаты.
- Остановка приложения и завершение разговора — разные операции: graceful shutdown не отправляет `room_closed` и не удаляет комнату из постоянного хранилища.

## 4. HTTP API v1

Ответы — JSON, ошибки имеют вид `{"error":"code"}`. Чувствительные ответы имеют `Cache-Control: no-store`.

| Метод и путь | Запрос | Результат |
|---|---|---|
| `POST /api/v1/rooms` | `{"title":"Вечер", "ttl_minutes":30}` | `201`, room, self, session_token, invite_token |
| `POST /api/v1/join` | `{"invite_token":"…"}` | `200`, room, self, session_token |
| `POST /api/v1/end` | Заголовок `Authorization: Bearer <session_token>` | `200`, `{"ok":true}`; закрывает комнату |
| `GET /ws` | WebSocket upgrade, затем authenticate | Поток событий |
| `GET /healthz` | — | `200`, `{"status":"ok"}` |

`room` содержит `id`, `title`, `expires_at`, `participants`, `messages`. `self` содержит `id` и `name`.

Основные ошибки: `invalid_input` (400), `session_invalid` (401), `origin_forbidden` (403), `room_unavailable` (410), `message_id_conflict` и `idempotency_key_conflict` (409), `rate_limited` и `capacity_reached` (429), `database_unavailable` (503). Недоступные/использованные приглашения не раскрывают подробности комнаты.

Лимиты различаются по причине: `room_full` — в комнате уже два участника; `message_limit` — достигнут лимит сообщений комнаты; `connection_limit` — исчерпан лимит WebSocket/подписок; `rate_limited` — превышена частота запросов или команд; `database_unavailable` — хранилище не готово. Клиент должен понимать, что можно повторить, а что требует другого действия.

## 5. WebSocket-протокол демо

Сначала, в течение пяти секунд после upgrade:

```json
{"type":"authenticate","session_token":"<64 hex characters>"}
```

Сессионный токен не передаётся в URL. После аутентификации сервер присылает `snapshot` с `payload: {room, self}`. Снимок истории и подключение к потоку выполняются атомарно.

Отправка:

```json
{"type":"send_message","client_message_id":"<UUID>","text":"Привет!"}
```

Сообщение сервера:

```json
{
  "type": "message",
  "payload": {
    "sequence": 1,
    "id": "<server ID>",
    "client_message_id": "<UUID>",
    "sender_id": "<participant ID>",
    "text": "Привет!",
    "created_at": "2026-09-20T12:00:00Z"
  }
}
```

| Событие | Payload / назначение |
|---|---|
| `snapshot` | `{room, self}` — состояние после подключения |
| `message` | Сообщение — получают оба участника |
| `ack` | То же сообщение — подтверждение приёма отправителю |
| `participants` | Массив участников после входа гостя; не индикатор online |
| `error` | `{code, client_message_id?}` |
| `room_expired` | `{}` — TTL истёк |
| `room_closed` | `{}` — чат завершён участником |
| `server_shutdown` | `{}` — сервер останавливается |

### Гарантии демо

- `ack` возвращается после добавления сообщения в память. Это не подтверждение прочтения, доставки собеседнику или записи на диск.
- Повтор `(participant_id, client_message_id)` с тем же нормализованным текстом возвращает прежний результат. С другим текстом — `message_id_conflict`.
- Каждое новое сообщение получает возрастающий `sequence` внутри комнаты. UI сортирует по нему и убирает дубликаты по `id`; `ack` и `message` могут приходить в разном порядке.
- При переподключении вся история комнаты заменяет локальный снимок. Неподтверждённые сообщения открытой страницы отправляются повторно с прежними ID.
- Текст обрезается по краям, не должен быть пустым, должен быть UTF-8 и занимать не более 4000 байт.
- Гарантия exactly-once по сети не заявляется. Отказ процесса уничтожает данные демо.

### Целевые гарантии версии 0.2

Эти правила фиксируют следующий контракт, но не утверждают, что он уже реализован в демо.

- `ack` означает, что сообщение принято и успешно зафиксировано PostgreSQL (`commit`). Это не подтверждение доставки собеседнику или прочтения. Фактическая durability зависит от настроек PostgreSQL, включая режим подтверждения записи и работу диска/репликации.
- Повтор отправки с тем же `(room_id, participant_id, client_message_id)` и тем же нормализованным текстом возвращает исходное принятое сообщение. Другая нагрузка с тем же ключом получает `message_id_conflict`.
- После потери HTTP-ответа повтор `create` или `join` с тем же ключом идемпотентности и тем же отпечатком запроса возвращает исходный результат в пределах окна повтора. Другой запрос с тем же ключом получает `idempotency_key_conflict`. После окончания окна повтор не гарантируется.
- Потеря WebSocket или рестарт backend не закрывают комнату и не отзывают сессию. После восстановления клиент получает актуальное состояние и продолжает работу с прежним токеном, если TTL не истёк и участник не завершил комнату.
- При истечении TTL или явном завершении доступ отзывается окончательно: поздние отправки и повторное подключение получают `session_invalid` либо `room_unavailable` согласно HTTP/WebSocket-контракту; действующий токен не восстанавливает доступ.

## 6. Состояния интерфейса

Клиент явно отображает одно из следующих состояний:

- `connecting` — устанавливается первое WebSocket-соединение;
- `connected` — сессия подтверждена, поток событий активен;
- `reconnecting` — временный сетевой или серверный сбой, сессия сохраняется и выполняются ограниченные повторы;
- `expired` — TTL истёк, доступ отозван окончательно;
- `closed` — участник завершил комнату, доступ отозван окончательно;
- `unavailable` — сервер или база временно недоступны, повтор возможен без удаления действующей сессии.

`reconnecting` и `unavailable` не означают истечение сессии. `expired`, `closed` и недействительный токен означают окончательную потерю доступа. Неотправленный текст и неудачное сообщение должны иметь отдельное состояние ошибки и не исчезать из интерфейса автоматически.

## 7. Ограничения и приватность

- Токены: 32 криптографически случайных байта; серверные индексы хранят SHA-256 токенов.
- `sessionStorage` хранит сессию и метаданные в пределах вкладки; история сообщений туда не сохраняется.
- WebSocket и API проверяют Origin по host. Запросы без Origin разрешены для небраузерных клиентов; Origin не заменяет аутентификацию.
- CSP, `textContent` вместо вставки HTML сообщений, отсутствие внешних скриптов и `Referrer-Policy: no-referrer`.
- Лимиты версии 0.2: 100 комнат, 500 сообщений на комнату; 400 сокетов суммарно и 2 на одну сессию для короткого перекрытия при reconnect. Бюджеты create, join, upgrade и команд отправки разделяются.
- Хранение: сообщения, события и записи идемпотентности хранятся не дольше TTL комнаты плюс 24 часа для завершения очистки и диагностики; после этого удаляются из основной БД по политике retention. Резервные копии и WAL подчиняются отдельной политике PostgreSQL и не считаются мгновенным физическим стиранием.
- Результат `create`/`join` для идемпотентного повтора доступен до окончания комнаты, но не более 24 часов после исходного запроса; после этого повтор не гарантируется. Открытые session/invite токены не хранятся в логах.
- Общий бюджет создания/входа/upgrade в демо: 120 запросов в минуту на процесс. В версии 0.2 бюджеты для восстановления действующих сессий не делят квоту с созданием комнат. Новые сообщения одной сессии — не чаще одного в 200 мс. Общие лимиты не заменяют защиту публичного сервиса от злоупотреблений.
- Очередь подписчика — 64 события; переполненный подписчик отсоединяется от потока, затем сокет закрывается и клиент восстанавливает историю. Сетевые записи имеют timeout 5 секунд.
- Ping раз в 25 секунд, timeout ответа 5 секунд; WebSocket-фреймы приложения не более 8192 байт.
- Прикладные логи содержат запуск, остановку и системные ошибки. Тексты, токены, IP и User-Agent не пишутся прикладным кодом; стандартный HTTP-сервер может журналировать аварийные ошибки. Публичное развёртывание требует отдельной проверки журналов proxy/runtime.
- HTTPS обязателен вне localhost. Backend видит открытый текст, сквозного шифрования нет. Не обещаются полная анонимность или физическое стирание памяти.

## 8. Критерии приёмки демо

- Запуск одной командой, без Matrix, БД и frontend toolchain.
- Два независимых браузерных контекста обмениваются сообщениями.
- Одноразовый вход и лимит двух участников выдерживают конкурентные запросы.
- Повтор сообщения не дублирует историю.
- Reload/reconnect восстанавливает текущую комнату и историю.
- TTL и явное завершение отзывают обе сессии.
- Медленный подписчик не блокирует остальных.
- Проходят `go test -race ./...` и `go vet ./...`.
- README честно описывает ограничения демо и запуск.

## 9. Критерии приёмки версии 0.2

- Перезапуск backend не закрывает активную комнату: после восстановления сервиса оба участника могут переподключиться с прежними сессиями до TTL.
- `ack` выдаётся только после commit сообщения в PostgreSQL; искусственный сбой до commit не оставляет сообщение, а сбой после commit допускает безопасный повтор по прежнему `client_message_id`.
- Временная недоступность сети/БД не переводит действующую сессию в окончательно отозванное состояние.
- Для заполненной комнаты, лимита сообщений, лимита соединений, частого запроса и недоступной БД возвращаются разные стабильные коды.
- Повтор create/join после потери ответа не создаёт вторую комнату или участника в пределах согласованного окна идемпотентности.
